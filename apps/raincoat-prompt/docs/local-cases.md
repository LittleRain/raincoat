# Raincoat Prompt 本地案例与评测题

2026-11-17 · 本地对话抽样 · 用于 [产品设计](product-design.md) 的首轮验证

## 样本范围

优先检查近期、有明确交付和追问的对话。Codex 和 ChatGPT 分别筛了最近 20 条会话索引，读取其中 4 条和 3 条的实际消息。WorkBuddy 从最近 38 条非后台会话中筛出相关工作区对话，以本地用户消息和会话元数据核对。Bitto 的本地日志隐藏了消息正文，从客户端读取了当前可见的库存任务及模型选择控件。Claude Code、Kimi、OpenCode 和 Antigravity 的本地样本也做了抽查。

这份表按任务特征选了 12 题，不能用于估算你使用各种 Agent 的频率，也不能用追问数直接推断模型质量。案例均为改述；评测另备脱敏材料、公开快照或合成数据。

## 首批 12 个案例

| 编号 / 场景 | 来源与初始任务 | 后续实际出现的要求 | 改写需要做到 |
| --- | --- | --- | --- |
| R1 · 调研 | Codex · 创作工作流工具。想构建可用于 Build in Public 的工作台，给了几种产品和 Skill 做例子 | 重新要求先拆创作流程，再扩展到例子之外。随后补充了主要运营平台 | 先拆实际流程，例子做搜索起点。目标平台未知时条件化呈现，避免把例子当成筛选范围 |
| R2 · 调研 | WorkBuddy · 知识库中的常驻 Agent 与 Claude 同类产品 | 补充了实际要比较的是常驻 Agent 的具体方向，并要求用外部信息补足 | 对齐要比较的能力，优先检索指定知识库，分别标注内部资料和外部一手证据 |
| R3 · 调研 | WorkBuddy · 最近一周某商品系列新品 | 从「一周内发售过」进一步问「一周内公布过」 | 将公告、开放购买和实际发售作为独立事件，覆盖能核实的日期。把后续新增范围视为另一种有效输入 |
| R4 · 调研 | WorkBuddy · 持续跟踪 Agent 框架动向和开发者案例 | 增加官方及社媒来源、实践筛选、日报 HTML，后又扩大到更广的 harness 范围 | 明确本期对象、来源、事实与讨论、持续追踪需要的去重与增量规则；只有明确提出时才涉及定时任务 |
| D1 · 数据分析 | ChatGPT · 估算某交易平台 Q3 GMV 或大盘 | 追问全平台规模与趋势，以及数据渠道、抽样口径、具体反推办法 | 给数据可得性、可计算的方法和抽样定义，明确区间、假设与复核步骤 |
| D2 · 数据分析 | Bitto · 库存分渠道和标签汇总 | 追问实物库存源字段，随后指定可售口径，要求汇总、明细和既有日更交付同步维护 | 先列字段来源、口径和最新共同可用分区。确认字段变动影响哪些产物，能对账，异常保留可查 |
| D3 · 数据分析 | WorkBuddy · 周度商品准入结构与业务增益 | 补充图例、季度同比环比、预售类型，以及一条新的交易额占比口径 | 原有口径逐项保留，明确分子分母、自然周与完整周期、可复算图表。把后来新增的维度放进扩展测试 |
| D4 · 数据提取 | Codex · 从审批列表筛指定平台和类目的记录，导出可预览的明细 | 再加勾选导出、指定字段和冻结选择列 | 准确复述纳入、排除、遍历、去重和表格交付要求。新增导出需求由用户输入驱动 |
| P1 · 写方案 | ChatGPT · 评估电商数据 Agent 机会 | 从「业务决策」拓展到查询、持续分析和优化，讨论全员开放及团队与个人的复用关系 | 从岗位与工作流出发，比较切入范围和复用方式，给可验证的最小试点 |
| P2 · 写方案 | WorkBuddy · 借体育赛事做电商营销 | 要求按不同赛果安排物料，并处理直购和抽赏混合的商品形态 | 做赛果分支，核对受众与商品形态，标注依赖的经营条件 |
| E1 · 开发 | Codex · 对比两个 Agent 调用组件并调整现有工程 | 追问最核心的几个场景、可以删的能力，之后再明确要求新分支落地和补 README | 判断当前阶段是评估还是实施。评估给用户场景与取舍，实施时才交代改动边界和验收 |
| W1 · 写报告 | WorkBuddy · 将会议录制整理成纪要并归档 | 纠正转写中的业务术语，并明确讨论的是周会中的业务增长归因 | 找指定录制和本地术语表，保留原意、会议范围及结论证据，区分讨论和已确认行动 |

有些追问纠正第一轮遗漏，有些是用户看到结果后才提出的新需求。回放只以当时已提供的信息评分。例如 D3 初版检查图例和已有指标的分母，季度维度应等输入明确后再加入；D4 初版检查现有交付规范，不能把后来提出的 Excel 操作计作第一轮必答项。

旧样本作为边界测试。Kimi 有按已有 PRD、线上截图和指定目录出原型的记录；它适合验证附件的范围和交付物。OpenCode 有数据迁移核对记录，可测试「核对所有表及漏项」这类验收条件。Claude Code 的本地数据以模型探测和零散技术提问为主，Antigravity 可读记录主要是试用问答，两者暂时适合验证短输入应留在通用场景。当前抽样无法确认 Claude 桌面端和其他仅存在安装痕迹的工具的会话内容。

## 四个首发改写候选

四个候选与通用改写使用同一份原始输入。以下起始输入是脱敏改述，验收项依据当时可见的任务信息编写。

### R1 · 按创作流程调查工具

起始输入「想搭个 Build in Public 工作台，覆盖选题、大纲、多平台发布和数据回收。帮我看看有哪些工具，我听说过几个创作产品和 Skill。」

> 先从 Build in Public 的实际工作拆开流程，覆盖素材记录、选题、大纲、平台改写、发布及反馈回收。把我提的工具当成线索，找每个环节已有的代表方案，并核对真实功能、支持的平台和需要手动接续的步骤。按能否当主工作台、与已有工具的衔接、维护成本给出可试的组合。平台尚未确认时标明适用范围，并指出哪个平台选择会改变推荐。每个关键判断附可核对的来源。

验收看是否覆盖全流程、能跳出用户举例、核实一体化与组合方案，以及是否对平台未知作了合适处理。

### R2 · 从知识库出发，外部信息补缺

起始输入「把知识库里提到的常驻 Agent 和 Claude 的同类产品整理对比给我。」

> 先在当前工作区可访问的知识库中找出已收录的常驻 Agent 和相关资料，列明每条结论对应的材料与日期。按常驻运行、事件触发或定时、任务状态和可复用的工作流比较。先用能核对的 Claude 能力作为对照，若有多个合理对象，说明各自适用的比较范围。一手外部资料可访问时，再补齐官方能力与最新变化。将外部补充和知识库已有信息各自注明。最后给出值得复用的模式和待验证缺口。

验收看是否先使用指定知识库、比较的是同层能力、外部信息的作用清楚、无法访问时给出实际缺口。

### D1 · 用公开信号反推平台交易规模

起始输入「有没有办法知道某交易平台 Q3 GMV 或其他大盘数据，通过什么数据推算？」

> 评估如何估算该平台 Q3 的全平台 GMV 及增长趋势。先列能查到的公开披露、可抽取的交易信号和间接代理量，注明覆盖范围、时点和口径。若可获得样本，设计可操作的抽样方法，写明抽样单位、分层、抽样时段、重复和退款处理，以及如何外推。给出两条可以交叉验证的估算路径、公式和需要的字段。只有数据足以支撑时才给估值区间，并列出最敏感的假设。数据不足时交付采数方案和可复算的计算表结构。

验收看能否把季度、全平台范围、可取数据、抽样、外推和不确定性落到可执行步骤，避免把历史预测或代理指标当实绩。

### D2 · 先查到同一口径，再生成报告

起始输入「把库存按商品标签和渠道拆一下，给我汇总和明细。」

> 用当前环境能读取的数据做一份库存汇总和明细。先列商品标签、渠道、可售和隔离数量的字段来源、粒度、公式以及最新可用的共同日期。说明缺分区、空值、重复键、多渠道重复计入和异常数的处理。汇总表按标签和渠道展示，明细保留可追到单品的字段，并校验两张表和总体是否能对上。输出标记实际数据日期，注明哪几项因数据不足还无法计算。

验收准备一份合成样本，包含同名异义字段、两表分区晚到，以及隔离数大于可售的异常。结果应明确源字段、保留异常供核查、证明汇总明细可对账。后续另测用户明确要求改日更任务时，是否同步更改同一口径的相关产物。

## 从案例落到自动匹配

| 原始输入里看到的信号 | 场景或适配 |
| --- | --- |
| 「有哪些工具」「对比」「从知识库找」并要求核对或补材料 | 调研。知识库是来源条件，与 Agent 名称分开抽取 |
| 「估算 GMV」「通过什么数据反推」 | 数据分析，加公开估算模块。是否可查数据由当前环境确定 |
| 「按品类/渠道拆」「占比」「同比」「带 limit 跑」 | 数据分析，加字段、粒度、分母和数据源模块 |
| 「分析数据，最后写报告」 | 数据分析为主，报告作为交付格式 |
| 「基于已确认材料出周报/纪要」 | 写报告。优先锁定材料、时间和事实 |
| 「这个方向值不值得做」或「方案怎么改」，有交付对象和选择 | 写方案；明确要求修改仓库或产物时才给开发适配 |
| 「1」「继续」等短接续语 | 保持通用或由用户保留现有场景。缺少上下文时，避免从最近 Agent 推任务意图 |

同一个模型标签出现于 WorkBuddy 的研究和 Bitto 的库存任务，实际可用资料、工具和交付物不同。这个例子优先测 harness 适配。WorkBuddy 也有两个不同模型标签下几乎同题的企业 Dashboard 调研，可作为后续同 harness 模型对照的起点。现有记录没有固定两次任务的工具、输入和运行条件，因此要用新的配对试验判断模型差异。
