# Raincoat Prompt 产品定位与落地方案

2026-11-17 · 产品设计提案 · 工作名 Raincoat Prompt

当前实现补充（2026-11-17）：五类场景已有本地基线与40题回归集，运行器已工程化；本阶段真实调用被执行沙箱阻塞，尚无新增有效回答，Agent/模型候选规则均禁用。下文为产品设计与后续路线，实际行为见 README、evaluation.md 和 prompt-generation.md。

首个可运行版本与本地构建方式见 [应用 README](../README.md)。本文也记录后续评测和改写能力的设计。

## 定位与首发用户

**给 Mac 上经常用 AI 做调研和业务分析的人，一个发任务前的快捷入口。按快捷键直接输入，客户端识别任务和当前或最近使用的 Agent，生成一份可编辑、可一键复制的 Prompt。**

首发用户是已经在用 ChatGPT、Codex 等工具的产品、运营、分析和独立研究者。从你自己的工作流出发，优先解决两类能复盘的返工。一次调研给了很多结论，却漏掉关键证据。一次数据分析给出了归因，却没把指标口径、比较基线和缺失数据交代清楚。对外承诺落在**减少必须追问的轮数和补证据的时间**，由实际任务结果验证。

把用户的失败分成四种原因，产品对每种原因采取不同动作。

| 失败原因 | 客户端怎么做 |
| --- | --- |
| 探索范围太窄 | 补上与决策相关的维度、反例和证据要求 |
| 分析方法欠缺 | 明确口径、对照、分解顺序和结论边界 |
| 运行环境缺能力 | 提示在哪个模式使用，或改用可见材料并标注缺口 |
| 原始信息缺失 | 对决定结论的事实提一个问题，或输出可直接使用的条件式指令 |

差异化假设是**针对复杂任务的场景模板，能在用户实际使用的 Agent 里稳定改善交付**。首发展示同一条原始输入在同一目标环境里的盲评结果、缺失项和追问次数。只有某一条适配有独立收益时，才把它作为产品卖点。现阶段市场证据来自公开产品文档，竞品效果和付费意愿待实测。

## 首版范围

打开浮窗即可输入。面板把识别的场景和目标显示为可改标签，常用路径无需选菜单。自用内测优先覆盖用户常用的 **ChatGPT、Bitto、WorkBuddy** 和通用预设。ChatGPT Deep Research 是明确模式，界面或用户选中时才启用其规则。WorkBuddy 用知识库调研和分析报告验证，Bitto 用工作区取数和交付验证。目标模型识别不到时，仍可直接用该 Agent 的适配。

| 场景 | 候选子场景 | 必须补齐的内容 | 阶段 |
| --- | --- | --- | --- |
| 调研 | 按任务流程做竞品调研、内部材料加外部核验 | 决策目标、示例与纳入范围、能力对齐、一手来源、缺口和反例 | 首版 |
| 数据分析 | 公开数据反推、有权限的数据取数与归因 | 数据可用性、锚点或分母、时间窗、字段来源、计算与复核方式 | 首版 |
| 开发 | Bug 定位、需求实现 | 复现或用户目标、仓库约束、变更边界、验收测试 | 已有本地基线，真实工具收益待测 |
| 写方案 | 产品、运营、技术方案 | 决策者、约束、可选路径、取舍、实施和验收 | 已有本地基线，收益待测 |
| 写报告 | 周报、专题报告 | 受众、材料、主要结论、事实与判断、待决策 | 已有本地基线，收益待测 |

首版先各做一个场景模板，用可选模块覆盖表中的子场景。同一任务涉及多个动作时，以用户要交付的结果选择主场景。例如「用这周数据解释 GMV 下滑，写给业务负责人」以数据分析为主，附加报告的受众要求。

预设识别和模板效果分别验收。首轮在 ChatGPT、Bitto、WorkBuddy 做原稿和优化稿对照，并在相同能力条件下横向比较主流模型。其他 Agent 的现有样本可用于边界验证，新增自动适配依据真实用量和稳定信号。样本依据和四份改写候选见 [本地案例与评测题](local-cases.md)。

## Mac 使用流程

1. 按全局快捷键时，先记下原前台应用及可取得的活跃窗口标识，再立刻弹出浮窗并聚焦输入。初始快捷键提议为 `⌃⌥Space`，可改，有冲突时可从菜单栏打开。识别与弹窗并行。
2. 用户直接打字。文本停顿约 300 毫秒后，本地更新场景标签，从明确的交付目标判断主场景。例如「调研这些竞品，最后给报告」仍走调研模板。原窗口的 Agent、模式和模型能识别时自动显示，用户可点标签修正。置信度低时保持通用场景或显示最近使用的目标。
3. `⌘↵` 用当前文字和标签优化。仅在缺口会改变结论时显示一个可跳过的问题。跳过后，输出会要求下游 Agent 先确认，或按可核实的条件给结果。
4. 用户看到可编辑的完整 Prompt 和一两条实际增补内容。按 `⌘↵` 或点「复制并关闭」写入系统剪贴板，回到唤起前的应用，由用户粘贴发送。复制后用短提示确认。

```text
目标  WorkBuddy ▾     模型  DeepSeek V4.1 Flash ▾     场景  调研 ▾

整理知识库里提到的常驻 Agent，顺便对比 Claude 的做法。

新增  先查知识库 · 按常驻运行能力对齐 · 用外部一手资料补缺
┌─ 可编辑的 Prompt ──────────────────────────┐
│ 先从当前工作区知识库找出已有资料……            │
└───────────────────────────────────────────┘
返回编辑                 复制并关闭  ⌘↵
```

窗口收起后短期保留草稿于内存。仅对已上屏的输入文本做分类，中文输入法的候选不触发。窗口识别绑定本次唤起，场景识别绑定当前输入版本。手动修正的标签锁定到这次草稿，开始优化时使用当时的文字和标签，屏蔽晚到的识别结果。断网、超时或云改写无效时保留原文并提供本地模板版。用户确认复制时才改动剪贴板。

### 识别当前 Agent、模式与模型

| 信号 | 用法 | 示例 |
| --- | --- | --- |
| 用户指定 | 浮窗手动选择或在原文明确指定投递目标时，当前草稿以此为准 | 「这条发给 ChatGPT」可改变目标。「调研 ChatGPT」只表示研究对象 |
| 当前窗口 | 以原前台应用标识为起点，再尝试读取已支持界面的可访问性控件。同一宿主内的多个模式，以及终端和浏览器，需要当前会话或页面的信号 | Bitto 界面有「选择模型」控件。浏览器或同时承载 ChatGPT 与 Codex 的应用，需要核对当前界面 |
| 单帧截图 | 用户启用并授权后，只对唤起前的受支持窗口读一帧。本机 OCR 只匹配标题、输入工具栏、模型选择器等区域内的已知标签 | 对话正文或历史气泡里提到的模型名与当前选择无关。模式不明确时沿用该 Agent 的通用模板 |
| 最近使用 | 记上次用户明确选择或确认复制时的 Agent、已知模式、模型和时间。优先沿用同一应用或模式最近的已确认目标，来源显示为「上次用于」 | 从文档或其他应用打开时可用最近的目标。已识别是 WorkBuddy 时，模型回退只查 WorkBuddy 的记录 |
| 通用 | 新用户、迟到或互相冲突的识别信号、无法确定的版本，以及不适用的旧记录均可继续优化 | Agent 可知而模型未知时，只套场景和 Agent 规则。历史模型仅作为候选，用户确认后才套专属规则 |

优先级为用户明确选择 → 当前窗口证据 → 最近一次确认 → 通用。用户在本稿中手选后，以手选为准。浏览器历史、其他标签页、未聚焦终端和定时任务都不更新最近目标。同一品牌的多个模式分别记录，记忆可在设置中关闭和清除。模型标签只说明界面显示的名字。只有明确可映射到已验证规则时才套用版本差异。

具体可用 AppKit 的 `NSWorkspace.frontmostApplication`，再按目标适配已授权的可访问性读取。截图采用 ScreenCaptureKit 单窗口单帧，Vision 在本机识别文字。截图和 OCR 原文留在内存并在识别后丢弃，持久化只保留用户确认的目标标签和时间。可访问性权限和屏幕录制权限分别按功能请求，拒绝、撤回或无法捕获时，仍用应用 ID、最近确认或通用继续。首版在真实机验证窗口定位、权限和不同界面布局。[前台应用](https://developer.apple.com/documentation/appkit/nsworkspace/frontmostapplication) · [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit) · [Vision 文字识别](https://developer.apple.com/documentation/vision/vnrecognizetextrequest)

首版交付菜单栏、浮窗、边输入边识别场景、自动建议目标、可选本机截图识别、可编辑结果和复制。复杂历史管理、同步、自动粘贴发送、任务执行和模板市场延后。对话扫描只用于这次的模板设计，日常使用客户端依赖当前窗口与自己的目标记忆。

## Prompt 如何生成

### 三个输入维度

| 维度 | 决定什么 | 设计举例 |
| --- | --- | --- |
| 场景 | 目标、工作方法和验收标准 | 指标归因需要可比基线和计算依据，竞品调研需要纳入标准和来源 |
| Harness | Agent 的执行环境。包括网页模式、工作区、工具、文件和权限 | WorkBuddy 先核对用户指定的知识库。Bitto 可按已确认的连接器读取数据，Codex 可按工作区和项目规范交付。应用识别本身不足以确认联网、SQL 或写入能力 |
| 目标模型 | 在该运行环境中实际执行任务的模型 | 某版本适用更精简的验收描述，某版本在复杂输出上受益于少量示例。每条差异由配对试验验证 |

目标模型和执行改写的模型是两项配置。首版用一个改写端，依据用户原文、场景模块、Agent 能力和已验证的模型规则，生成一份可编辑、可直接复制的文案。场景规则以通用任务和可检查的交付为起点。模型规则结合官方指南、公开实践及同环境对照，个人案例用于回放。优化器的工作指令和不同目标的成稿见 [Prompt 生成规则与文案](prompt-generation.md)。

## 模板内容从哪里来

1. **你的常用任务和返工记录。** 选曾经漏证据、口径跑偏或复核困难的案例。写下原问题、需要补问什么、你最终认可的输出和环境。在自己的私有样本里验证，公开演示使用合成或经授权脱敏的材料。
2. **官方文档。** 收集模型提示指南、目标环境的模式和工具文档、版本说明；把每条建议变成一条可检验的规则。官方 Deep Research 示例也展示了先补足查询和交付要求再提交研究 Agent 的做法。[OpenAI Deep Research 示例](https://developers.openai.com/cookbook/examples/deep_research_api/introduction_to_deep_research_api_agents)
3. **作者真实案例。** 把用户提供的两条 X 原帖和后续找到的公开实践作为候选方法的来源，优先收录附有原始任务、模型或环境、验收或可见产物的案例。每条记录保留来源、改写动作和回放判据。公开用例及回放方式见 [Prompt 生成规则与文案](prompt-generation.md)。

## 先证明效果，再维护版本

### 第一轮对照试验

评测分为日常 Agent 的前后对照、共享环境的主流模型对照，以及可实际运行的 Agent 与模型组合。用公开任务、合成问题和 [脱敏对话案例](local-cases.md) 回放。矩阵、题库和评分标准见 [Prompt 效果评测](evaluation.md)。

| 版本 | 意图 |
| --- | --- |
| A 原始输入 | 看现有 Agent 的默认表现 |
| B 通用改写 | 用同一改写模型，只要求澄清、结构化任务 |
| C 加场景模板 | 测调研或分析框架的增益 |
| D 加 Agent 适配 | 测明确资料入口、工具和交付方式的增益 |
| E 加模型规则 | 测指令表达改动的增益，有候选模型规则时运行 |

C 对 B 测场景价值，D 对 C 测 Agent 适配，E 对 D 测模型规则。运行 E 时固定目标模型和 Agent 环境，仅切换模型规则。首轮可先跑 8 道开发题的 A/B/C，剩余组合等有质量信号后补齐。

首批用例可以从这些问题取材，先把判分答案写在看不到的地方。

| 输入 | 需要判分的结果 |
| --- | --- |
| 「帮我看看这个 Mac 工具方向能不能做」 | 区分两种直接替代方案，核实关键功能，说明什么证据会改变投入决定 |
| 「两份公开资料对同一个指标说法不一样，哪个能用」 | 核对发布年代、时间范围和定义，指出差异可以或无法解释的部分 |
| 「上周转化率为什么掉了」＋两份同名指标不同分母的表 | 找出分母差异，给出可比较的再计算结果，缺字段时说明缺口 |
| 「按商家拆一下 GMV 跌幅」＋天级数据有缺口的 CSV | 先发现缺天，使用完整的可比口径，在数据允许时拆解并回加验证 |

用真实交付物打分。调研核对证据覆盖率（命中且有来源支持的必答项 ÷ 全部必答项）、引用是否支持主张，无来源的关键结论单记。数据分析核对关键数字、口径、比较周期、贡献项以及能否复算。通用硬指标是保留用户约束和事实、无捏造来源或数字、尊重实际工具能力。另记总追问轮数、从输入到接受结果的时间和模型调用成本。机器先查链接、结构或数值，人工用匿名结果做配对盲评。后续可用模型评审，先校对人工一致性并打乱输出顺序。[OpenAI 评估实践](https://developers.openai.com/api/docs/guides/evaluation-best-practices) · [Claude 评估指南](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests)

建议 C 相对 B 在至少 60% 的题上更好，平局计入总题数，且没有新增关键错误。Agent 适配和模型规则分别达到可复现的收益后再发布，缺少验证时保持已通过的版本。小样本用于决定是否继续投资，公开效果承诺需要更多独立用例。若 C 与 B 基本持平，先改善样本和模板，暂停扩大开发范围。

### 模型或 harness 更新后的工作流

| 步骤 | 执行方法 |
| --- | --- |
| 发现 | 维护者每周看一次官方更新，记录模型发布或弃用、目标界面和工具变化。默认模型替换、工具不可用或明确回归时，建议两个工作日内跑关键用例。内测可先手动，之后再加只创建待评测记录的定时脚本。 |
| 复跑 | 根据影响范围选择受影响的用例。优先在新目标跑现有稳定模板，再用同样环境跑候选改动，保留旧目标稳定结果用于定位变化。记录目标模式、可观测的模型和版本、工具配置、测试日期、模板及改写端版本。 |
| 修订 | 先区分模型行为、工具权限、数据变化或模板错误。只有可用新规则解释并复现改善时才改规则；工具变动先改能力描述。 |
| 验证 | 真实客户端的现场测试是对应预设的验证依据。Codex CLI 的非交互模式和 Claude Code 的程序化模式可用于其自身的自动回归。网页模式、桌面模式分别维护少量人工测试；无法固定模型快照时记录模式、可见模型名和日期。 |
| 发布 | 你审核通过后打独立模板包版本。客户端内置可用包，验签、版本兼容及 schema 检查通过才原子切换，出问题回退上一版。内测先随 App 发，更新节奏稳定后再开模板独立更新。 |

上游观察入口包括 [OpenAI API 更新](https://developers.openai.com/api/docs/changelog)、[ChatGPT 与 Codex 更新](https://learn.chatgpt.com/docs/changelog)、[Codex CLI 发布](https://github.com/openai/codex/releases)、[Claude Code 发布](https://github.com/anthropics/claude-code/releases)、[Codex 非交互模式](https://learn.chatgpt.com/docs/non-interactive-mode) 和 [Claude Code 程序化模式](https://code.claude.com/docs/en/headless)。

### 从用户输入发现新场景

1. 本地保留聚合计数，如用户改选场景、重试、手动改写，以及自愿选择的原因「漏了证据」「口径不对」「环境缺工具」。复制是使用意向的信号，实际发送和任务结果由用户另行反馈。使用统计和反馈默认只留本机，收集案例由用户主动分享。
2. 每周从自用记录和用户主动分享的脱敏案例里找重复失败。发现至少 3 个独立例子且需要不同的验收标准时，提出一个候选子场景。这个数字是内测的起步阈值。
3. 对现有模板和候选模块跑配对评测。如「周度指标对比」主要改变基线，把它加成模块即可。如「确认数据异动能否归因给活动」经常需要实验或对照设计，且现有模板反复给错结论，再考虑独立场景。合并和发布由你审核。

## 技术落地与分发

| 部件 | 第一版 |
| --- | --- |
| macOS 客户端 | SwiftUI 做表单、设置和预览，AppKit 做浮窗、焦点与系统剪贴板。注册可配置的系统级快捷键，先用一轮实机技术验证确定最低系统版本及权限表现。[NSPanel](https://developer.apple.com/documentation/appkit/nspanel) · [NSPasteboard](https://developer.apple.com/documentation/appkit/nspasteboard) |
| 生成 | 本地模板和规则引擎可离线使用，以普通模板填充原文并提示未知条件。增强版调一个低延迟改写 API，内测用用户自带 API Key，Keychain 保存。请求仅在用户发起优化时提交已输入的文本及所需规则。设置标明供应商和网络处理方式。云端请求失败可在浮窗切换本地整理。[Keychain Services](https://developer.apple.com/documentation/security/keychain-services) |
| 模板 | Git 维护 JSON 元数据与 Markdown 文案，校验规则 ID、引用关系与依赖版本。模板包是数据，客户端可选取和渲染。实际业务用例和评测输出保留在授权的私有位置。 |
| 评测 | 最早用表格或 JSONL 记录输入、目标、版本、运行和评分。足够复现后再做 CLI 和 CI，优先自动化固定资料的回归。成本按每次改写以及每次下游任务分别记，试运行后设置维护预算。 |
| 分发 | 先用内部构建自测。面向外部用户时，采用 Developer ID 签名和公证后的 DMG。在个人 Mac 验证安装、快捷键、离线和降级后再发内测包。[Apple 分发说明](https://developer.apple.com/developer-id/) |

建议的运行路径为「浮窗 → 并行识别目标和场景 → 模板规则选择 → 本地整理或 API 改写 → 校验和预览 → 系统剪贴板」。打开浮窗并可打字的目标 p95 小于 300 毫秒。在线改写 p50 小于 3 秒、p95 小于 8 秒，均从真实机器和网络测量。发送给改写 API 的内容以用户输入和命中规则为限。实际执行时由用户在目标 Agent 中自行提供文件、启用连接器并发送。整个内测可在无自建后端和无账号体系的情况下运行。

## 落地顺序和验收

| 阶段 | 实际交付 | 过关条件 |
| --- | --- | --- |
| 第 1 周 · 验证内容 | 用本地真实案例回放 A/B/C。写两个场景基底、四个改写模块和首批评测题 | 能指出各模板改善或遗漏的实际交付项 |
| 第 2 周 · 做到可用 | 原生浮窗、快捷键、实时分类、前台应用及最近目标识别、离线模板、编辑复制 | 中文输入、复制、焦点、全屏、双屏和离线在自己的 Mac 上通过 |
| 第 3 周 · 验证适配 | 加授权后的窗口读取、本机截图识别和单一改写端，核对三个常用 Agent 的模式识别与真实结果 | 覆盖当前模型切换、旧模型回退、浏览器非 Agent 页、终端多会话、读屏拒绝、迟到回调和手改标签。得到 C 对 B 和 D 对 C 的对照，有模型规则候选时做 E 对 D |
| 第 4 周 · 私测 | 让 5–10 名常做此类工作的用户拿自己的任务试两周，记录结果与复用 | 暂定至少一半激活用户在第二周主动复用，配合可接受的首轮结果比例与追问次数判断 |

这是单人开发和小样本验证的排期估算，取决于现成用例、API 和签名准备情况。**核心指标是用户接受的首轮结果比例**，口径为所有收到反馈的实际任务中，无需实质追问即可用于下一步的比例。同时记反馈覆盖率、每个接受结果的追问数，以及唤起到复制的时间。两周内测安排可跨过第四周；上线范围以质量和使用验证为准。

长期收费假设是用户为经持续验证的专业场景与兼容性更新付费。先用公开的同题结果和短演示招募真实用户。只有复用和付费访谈支持持续价值时，再测试免费通用版、付费专业模板更新或按量托管改写。试验过程记录真实成本与额外等待时间，便于决定是否继续提供托管改写。

**第一批回放**用创作工具、常驻 Agent、平台 GMV 和库存取数四题。先看模板能否减少补充范围、抽样方式和口径的轮数，再加当前目标适配。另用一组界面快照测 Agent、模式、模型的识别，分别记录准确率、识别覆盖率和手动修正次数。把能正确留空的情况单列，避免为了提高覆盖率猜一个模型。
