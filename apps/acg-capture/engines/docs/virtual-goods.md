# 游戏虚拟商品：tab 设计与实施方案

> 状态：**已按 2026-11-18 最终口径改造并落库**。一级 tab「游戏虚拟商品」，两个子 tab（抓取任务 / 游戏汇总）。
> 台账写企微「官方抽赏类商品追踪」的 `游戏虚拟商品` 子表（`ty2XMk`）：**9 列，一个商品名一行，价格全在备注**。
> 没有游戏订阅库；每周把行业里有热度的游戏抓一遍（不限新老），只补表里缺的商品行。
> 本文是口径与结构的唯一说明，代码从属实现。

## 0. 决策记录

| # | 决策 | 结论 |
|---|---|---|
| 1 | 场景定位 | 抓游戏内购商品：充值代币、月卡、通行证、礼包。 |
| 2 | 台账落地 | 只保留 `游戏虚拟商品` 子表；**9 列**：游戏 / 商品类型 / 商品名 / 购买渠道 / 证据链接 / 原文引用 / 状态 / 入库日期 / 备注。 |
| 3 | 一个商品一行 | 去掉「档位」列：同一商品的不同面额/渠道价格写进备注（`60 档 6 元（App Store）；300 档 30 元…`），判重键＝游戏 + 商品名。 |
| 4 | 不维护游戏库 | 表里的游戏名就是清单；不存 active/candidate/paused，不做逐游戏渠道配置。 |
| 5 | 每轮抓什么 | **行业里有热度的游戏都抓一遍，不管新老**；抓到后按商品名去重，只把表里缺的行补进去，不更新已有行。 |
| 6 | 热度门槛 | 发行商在关注名单（关键词包含匹配）/ 预约量 ≥ 10 万 / 畅销榜名次 ≤ 50，至少一条；**App Store 页不算热度**。 |
| 7 | 抓取通道 | 三条：`store`（App Store 中国区内购页确定性解析，零模型）、`workbuddy`（翻官网/公告）、`DeepSeek`（搜索反查）。 |
| 8 | 官方口径 | A 官网/商城/充值中心、B 官方社媒、C 应用商店内购页（模型来源需双源）、D 游戏内/需登录只能人工。 |

## 1. 第一性原理：表是商品清单，每周补缺

1. 虚拟道具不出新品，价格档位长期稳定，所以不需要「按游戏持续刷新」，但**行业里的热门游戏会换**：每周都有新游上榜、老游新版本加档位。
2. 因此每轮的做法是：把当前有热度的游戏都过一遍，抓它们的商品，和表里已有的「游戏＋商品名」比，**只补缺的行**。
3. 这样既不需要维护「追踪名单」，也不会因为「抓过一次就跳过」漏掉后来加的商品；代价是每周都有抓取成本，靠 `maxNewPerRun` 与热度门槛控量。
4. 同一个商品名一行，价格是「多值」：不同面额、不同渠道都拼进备注，避免为每个面额建一行。
5. 只记官方标价，不记到手价；首充双倍、赠送、限购写备注。

## 2. 数据模型

### 2.1 商品台账（企微 `游戏虚拟商品` / `ty2XMk`，9 列）

| # | 字段 | 类型 | 说明 |
|---|---|---|---|
| 1 | 游戏 | text | 官方全名；去重后就是游戏清单 |
| 2 | 商品类型 | single_select | 充值代币 / 月卡 / 通行证 / 礼包 / 其他 |
| 3 | 商品名 | text | 官方名（创世结晶 / 空月祝福 / 珍珠纪行）；**一个商品只留一行** |
| 4 | 购买渠道 | text | App Store 中国区 / 官网 / 官方社区（多行合并时取首条） |
| 5 | 证据链接 | text | 可打开的官方页面 URL |
| 6 | 原文引用 | text | 含商品名 + 价格的原片段（取最长的一条） |
| 7 | 状态 | single_select | 在售 / 预约 / 下架 / 存疑 |
| 8 | 入库日期 | date_time | 首次入库日期；补行时写当天，已有行不动 |
| 9 | 备注 | text | **所有价格**（`60 档 6 元（App Store）；300 档 30 元…`）+ 折算 + 首充/限购 |

写入约定：

- 判重：`norm(游戏) + norm(商品名)`。命中即 `duplicate`，**不写表、不改已有行**。
- 只做新增（`add_items`），没有更新已有行的路径；要改价格就在表里手工改。
- 商品名归一（2026-11-18 追加，2026-11-18 晚收紧）：**一个币种一行，面额不进商品名**。
  `980创世结晶` / `充值1980枚龙晶` / `980枚古老梦华` / `3,150元宝`（千分位）/ `点券x60` / `勾玉×6480` /
  `6800NZ点（赠送288NZ点）` 一律归一成币种名（`创世结晶` / `龙晶` / `古老梦华` / `元宝` / `点券` / `勾玉` / `NZ点`），
  面额与价格进备注（`1980 档 198 元（App Store）`）。礼包/月卡这类不是币种，保持原名；
  `30元月卡` 归一成 `月卡`（价格进备注），`3星必得招募礼包` 这类数字开头的礼包名不动。
  归一在抓取时（`canonical_product`）与写表迁移时（`--init-table` → `_normalize_products`）走同一条规则。
- 多档合并：候选里同一商品的不同面额先各自验收，再 `combine_products` 合成一条，价格收进 `prices[]` 写成备注。
- 迁移：`--init-table` 幂等——先把「官方价」并进备注、再把同商品多行合并（删除多余行）、删「档位」列、最后做商品名归一（2026-11-18 累计：48 → 26 → 84 行；`充值1980枚龙晶` 等 4 档合并成一行 `龙晶`）。

### 2.2 游戏清单（派生）

`vg_table.games_from_items(items)`：每游戏商品数、各类型数量、最早入库日期、渠道集合、缺哪几类（代币/月卡/通行证）。当前 5 个游戏 26 行：原神 5、崩坏：星穹铁道 5、鸣潮 4、第五人格 2、明日方舟 10。

### 2.3 渠道与门槛（`references/vg-sources.json`）

`discovery`：版号公示、TapTap 新品、App Store 畅销榜、B 站游戏中心、发行商关键词。
`thresholds`：`windowDays`（提示词里的参考窗口，不再作为硬条件）、`minReservation` 100000、`chartTop` 50、`maxNewPerRun` 10。
`channels`：A/B/C/D 四级；只有 `confirmed` 且 A/B/C 参与抓取，C 级模型来源需双源。

## 3. 流程（每周一轮）

```
1. 读台账 → 现有行（判重键＝游戏+商品名）与游戏清单
2. 发现：workbuddy 与 DeepSeek 并行，列出当前中国大陆有热度、且有内购的游戏（不限新老）
3. 过门槛：发行商名单 / 预约量 / 榜单名次（至少一条）；候选去重
4. 首抓（对每个过门槛的游戏）：
   store    有 appStore 就拉内购页，确定性解析「名称 ¥价格」
   workbuddy 只派一个 job 覆盖全部游戏，给全部官方渠道与商品名提示
   DeepSeek  每游戏 3–4 组查询，抽取结构化候选
5. 合并：同商品不同面额先按「游戏+商品名+档位」合并双源，再逐条验收
6. 验收：官方域名 + 原文命中 + 商品名/价格/面额 + 代币折算自洽；二手判废；**DeepSeek 的非官方来源直接判废（只留线索、不占待确认）**；C 级模型单源进待确认
7. 合成：combine_products 把一个商品的多档合成一行，价格列表进备注
8. 写表：按「游戏+商品名」查重；只 add 缺的行；已有行不动
```

结论形态：没有新行是正常（表已覆盖）；有缺口就补；拿不到证据进待确认。

## 5. 运维

- 表迁移：`--init-table` 幂等；2026-11-18 已把 48 行合并为 26 行、删「档位」列、保留「入库日期」。
- 初始化 / 按清单补抓：`--games-file`（CSV 或 JSON）跳过发现层，按清单逐个游戏抓，不再受每轮 20 个上限限制。
  清单缺 `appStore` 时用 iTunes 搜索补，**只接受名称完全一致的 App**（攻略/图鉴/云游戏版本一律拒绝）——
  系列名或端游（塞尔达、魔兽、DOTA）因此解析不到商店页，交给 workbuddy / DeepSeek 通道。
  workbuddy 按 12 个游戏一批顺序派发，避免单 job 里模型只回前几个。
- 验收口径两档：`--policy strict`（默认，每周例行）只认已配置的官方渠道；`--policy open` 不卡渠道归属，
  只要来源页能打开、页面里同时出现商品名与价格、面额/折算自洽就采信，渠道按域名分级（平台商店 0.9 / 其它 0.72）。
  open 下模型给的 quote 常是搜索摘要，页面里对不上原句时退一步判「页面同时有商品名+价格」，并在条目上留 `evidence=page_name_price`。
- 重判不重抓：`--reverify <runId> --policy open` 用已经落盘的候选按新口径重跑验收再写表（先并发预取来源页，
  同一个 URL 只取一次），口径调整或批次等待超时都不必再花一次模型钱。
- 限流：App Store 429 → 游戏间 1s、退避 6s 重试一次；仍失败记 `rate_limited` 进待确认。
- 人工裁决：只有 `pending_review` 可 accept/reject；accept 且 `--write` 才写表。
- 渠道库：A/B/C 且 confirmed 才可用；C 级单源靠 store 通道补强。

## 6. 实测（2026-11-18）

- 表迁移：48 行 → 26 行（合并删除 22 行），9 列；创世结晶一行含 6 档价格。
- 真实抓取（workbuddy + DeepSeek，`--write`）：见当轮 run.json 与表行数变化。
- 已知历史缺口：第五人格缺月卡/通行证（App Store 未公示）、明日方舟缺代币（源石只有礼包名）。按「补缺」逻辑，后续轮次若发现对应商品会自动补行。
